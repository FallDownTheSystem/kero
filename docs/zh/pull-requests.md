# 拉取请求

Kero 通过仓库所在主机上的 [GitHub CLI](https://cli.github.com)（`gh`）处理仓库在 GitHub 上的拉取请求，因此那里需要安装 `gh` 并已登录。每个操作都以你的身份使用 `gh`，因此能做什么由 GitHub 决定，Kero 也只提供这些操作。

<a id="review"></a>

## 审查标签页

右侧边栏的**审查**标签页，或 <kbd>⌥</kbd> <kbd>⌘</kbd> <kbd>P</kbd>（Windows 和 Linux 上为 <kbd>Ctrl</kbd> <kbd>Shift</kbd> <kbd>K</kbd>），会列出你所在窗格的仓库打开的拉取请求。列表来自分支推送到的远程仓库，通常是 `origin`；列表上方的仓库名可以选择该仓库在 GitHub 上的其他远程。**打开的**、**我的** 和 **待我审查** 用来筛选列表，列表中显示每个拉取请求的分支、检查和审查状态。在列表中右键点击拉取请求，可以合并、更新分支、标记为可审查或转为草稿，以及关闭。

## 拉取请求页面

点击拉取请求会在窗格旁边的查看器中显示它；旁边的箭头会在 GitHub 上打开它。**对话** 显示它的描述、每位审查者的审查状态（已批准、要求更改或等待审查）、它的检查（点击可展开列表），评论和审查，以及针对行和文件的评论串，回复显示在它所回复的评论下方并与之分隔；点击评论串的位置可在 **文件** 中查看。**文件** 显示它的改动（与其基础分支一起获取），每个文件的差异中，行内评论显示在对应行的下方，针对整个文件的评论显示在差异上方。之后行已变化的评论串只显示在对话中，并标为已过时。**解决对话** 会在 GitHub 上解决评论串，之后它折叠为一行。标签页旁的箭头可在你的评论和已发布的评论之间逐条跳转。当仓库的某个工作树检出了拉取请求的头部（例如审查用的工作树），可以右键点击文件打开它，或把它拖到窗格上；否则文件不在磁盘上，无法打开。

<a id="reviewing-with-an-agent"></a>

## 用智能体审查

拉取请求上的**审查**会让智能体审查它。点击后，Kero 会获取拉取请求的分支，并在该分支的[专属工作树](./worktrees.md)中的新会话里启动智能体。每次审查都会把拉取请求检出到自己的分支 `review/pr-<编号>`（之后是 `review/pr-<编号>-2`，依此类推），所以同一个拉取请求可以审查多次，即使你的检出或另一个工作树正在使用它的分支也可以。从改动标签页推送该分支，会推送到拉取请求的分支；用 git 时，运行 `git push origin HEAD:<分支>`。连同工作树关闭审查时，只要拉取请求的分支已有它的提交，就会删除该分支。右键点击按钮或拉取请求，可以改为把审查发给你所在窗格的智能体，或在窗格所在文件夹的新会话中启动智能体。审查开始前会显示提示词供你编辑。新会话的智能体会把提示词作为命令参数收到，因此立即开始审查，无需向它输入任何内容；你所在窗格的智能体则会收到粘贴的提示词。

审查拉取请求的会话在侧边栏中标为**审查**，并列在拉取请求上方的**审查智能体**中，显示与侧边栏相同的状态和智能体的最后一条消息。点击它会转到该会话；它的菜单可以查看拉取请求，或关闭会话（会询问是否一并删除工作树）。有审查智能体的拉取请求，在其行和页面上以**智能体**代替**审查**，点击即转到该智能体。会话已关闭但保留了工作树的审查会留在列表中，可以在该工作树中再次审查，或删除它：**删除工作树…**会先询问，并说明会丢失多少有改动的文件。审查一个已有审查的拉取请求时，可以打开它的智能体，或在它的工作树而不是新工作树中审查。

<a id="repository-setup"></a>

## 仓库设置

**仓库设置…**（审查标签页中的齿轮）为每个仓库设置智能体命令和审查提示词，因为不同仓库使用的技能和工具不同，例如 `/code-review high {ticket}`。提示词中的 `{number}`、`{url}`、`{title}`、`{branch}`、`{base}` 和 `{author}` 会换成拉取请求的值，`{ticket}` 会换成标题、描述或分支中的第一个问题键，例如 `PROJ-123`；如果都没有，审查会请你输入。命令默认为 `claude`。Kero 把提示词作为一个参数放在命令之后，Claude Code 和 Codex 都这样接收首个提示词；若命令在别处接收，请放上 `{prompt}`，例如 `codex exec {prompt} --full-auto`。命令中同样可以使用拉取请求的占位符。

它还可以设置仓库的默认合并方式 `repo-merge-method`，并为该仓库替换提交信息、拉取请求和审查的提示词（[提示词](#prompts)）。

## 检出

拉取请求菜单和页面中的**检出**不启动智能体，像 `gh pr checkout` 一样把它检出到以拉取请求命名的分支上：拉取请求自己的分支（推送后会更新拉取请求），来自复刻的则为 `pr-<number>`。**在此处检出**会检出到你所在窗格的工作树；只要该工作树有未提交的改动，Kero 就不会检出，请先提交或储藏，或者在新工作树中检出。已有的分支若落后于拉取请求，会被快进到它，若有自己的提交则保持不动。**在新工作树中检出**会在该分支的[专属工作树](./worktrees.md)中开始一个会话。如果某个工作树已经有这个拉取请求（在它的分支上、在推送到它的分支上，或是审查的工作树），Kero 会转到那里：转到在其中工作的会话，没有则新开一个。

<a id="merging-and-other-actions"></a>

## 合并及其他操作

在拉取请求页面的标题下方，会显示它能否直接合并，以及不能的原因：冲突、必需的审查或检查、分支落后于基准，或仍是草稿。按钮用于合并、将草稿标记为可审查、重新打开已关闭的拉取请求，或删除、还原已合并的拉取请求的分支；旁边的 **⋯** 里是其余操作：**合并…**、**启用自动合并…** 或 **停用自动合并**、**更新分支**（也可通过变基）、**转为草稿**、**关闭拉取请求…**、**还原…** 和 **删除分支…**。**合并** 会询问使用仓库允许的哪种方式（压缩、合并提交或变基），以及合并后是否删除分支；它只在你看到的那个提交上合并，之后若有推送就会停止。在条件尚未满足时，**启用自动合并** 会让 GitHub 在满足条件后合并。分叉的拉取请求若有工作流运行在等待维护者批准，会显示 **批准运行**，因为它们会运行分叉的代码，所以会先询问。

**合并** 以仓库的默认合并方式 `repo-merge-method` 开始，它由[仓库设置](#repository-setup)设置；用其他方式合并时勾选 **设为此仓库的默认方式** 也可以。没有设置时，使用仓库允许的压缩、合并提交、变基中的第一个。

<a id="draft-reviews"></a>

## 草稿审查

智能体从不发布到 GitHub。它的评论通过 [Kero 的技能](./agents.md)教它使用的 `kero pr comment` 进入 Kero 保存的草稿审查；Kero 会检查每条评论都在拉取请求差异的行上（这也是 GitHub 唯一接受评论的行），或在拉取请求改动的文件上。默认提示词让智能体先审查整个拉取请求，再把每条想留下的评论对照代码核实，然后才添加。

智能体添加的评论会立即显示在拉取请求的 **文件** 中，并标为 **智能体**。和改动标签页中一样，你可以编辑或删除任何一条，也可以从某一行的边栏，或用文件标题中的评论按钮针对整个文件，添加自己的评论。智能体评论上的闪光图标会把关于它的问题输入到智能体的窗格中，由你写完。拉取请求下方的栏里有审查的摘要（即 GitHub 上审查的正文）和结论：**评论**、**批准** 或 **要求更改**（自己的拉取请求只能评论）。**发布审查** 会先确认，然后把摘要和评论作为一次审查发布，因此作者只会收到一次通知。审查不需要评论：可以在栏中直接批准，或只留下摘要。审查列表会标出草稿中有评论或摘要、或其智能体仍在工作的拉取请求。栏中的 **开始草稿** 会在不启动智能体的情况下开始草稿，你自己的智能体可以用 `kero pr comment --pr <编号>` 添加评论。栏菜单中的 **丢弃审查…** 会删除草稿。

<a id="review-guides"></a>

## 审查导览

拉取请求的 **导览** 标签页是一次讲解，让你不必逐行阅读就能理解它：先是概要，再按阅读顺序排列各站，每一站指向值得阅读的行并附有说明。**编写导览** 会像审查一样，在拉取请求的工作树中让智能体编写导览，指示为 `pr-guide-prompt`（设置 › Git）；智能体用 `kero pr guide` 编写，导览不会发送到 GitHub。标签页一次显示一站及其行的摘录，上方是站点列表和 **下一站**；标有 **需仔细看** 的站点需要维护者做出判断。**完整差异** 显示该站的整个文件，可以像在文件标签页中一样评论；**评论** 会在你的审查草稿中针对该站的行开始一条评论，**询问智能体** 会把关于该站的问题输入到智能体的窗格中。拉取请求改动之前写的导览会注明这一点，并提供 **重写导览**。菜单中的 **丢弃导览** 会删除它，审查草稿会保留。

<a id="pull-request-notifications"></a>

## 通知

Kero 每 5 分钟检查一次你的项目所在的 GitHub 仓库，并在有新的拉取请求请求你审查时通知你。设置 › Git 中可以设置哪些拉取请求会通知你 `pr-notify`（请求你审查的、别人打开的所有新拉取请求，或者都不通知，此时也停止检查），以及检查间隔 `pr-poll-interval`。点击通知会在该项目的会话中显示这个拉取请求。Kero 会记住已经看到的拉取请求，所以重启后不会再次通知；对一个仓库的第一次检查只会记下当前打开的拉取请求。

<a id="a-session-s-pull-request"></a>

## 会话的拉取请求

会话知道自己的拉取请求。会话的分支推送后，如果它在 GitHub 上有打开的拉取请求，Kero 就把它链接到会话；用**新建拉取请求**创建时会立即链接。切换到其他分支后链接会解除。你也可以手动链接，手动链接不会因分支变化而被替换：拉取请求页面上的关注按钮把它链接到你所在的会话，或取消链接，`kero pr link` 和 `kero pr unlink` 也一样。会话的提示会显示检查状态，会话菜单可以显示它或取消链接。

会话打开期间，Kero 每分钟关注一次它的拉取请求，并在检查失败或因冲突无法合并时，通过[智能体自己的接收方式](./agents.md#how-agents-get-keros-messages)向会话中的智能体发送消息，以此唤醒它。消息以“Kero PR watch:”开头。智能体回到提示后才会收到，工作中或正在向你提问时不会收到。设置 › Git 中的 `pr-watch-wake` 决定什么会唤醒它：`all` 在检查通过以及有除你之外的评论或审查时也会唤醒；`failures` 只在检查失败和冲突时唤醒；`off` 什么也不做。仅因评论唤醒，每个拉取请求最多 10 次，这样回复智能体的机器人就无法让它一直运行下去。没有智能体的会话会改为通知你。

<a id="new-pull-request"></a>

## 新建拉取请求

**新建拉取请求** 为你所在窗格的分支创建拉取请求。表单显示要合并到的分支，起初是推送目标仓库的默认分支；点击它可以选择其他分支或其他远程的仓库。默认分支排在最前，其后按最近改动排列，输入文字可以筛选。标题和描述下方列出拉取请求带来的提交及其改动的文件，点击文件可展开其差异。只有提交会包含在内：表单会显示有多少文件尚未提交，以及有多少提交还不在推送目标上。标题旁的闪光图标会撰写标题和描述，方式与 **撰写信息** 撰写提交信息相同，使用 `commit-message-command`。只有一个提交的分支会以该提交的主题作为标题。

**创建拉取请求** 会先推送推送目标上没有的提交，然后用 `gh` 创建拉取请求并打开它。旁边的箭头中有 **创建为草稿** 和 **在 GitHub 上显示**；后者会打开 GitHub 创建拉取请求的页面，标题和描述已填好，由你在那里完成。如果分支已有打开的拉取请求，表单会改为显示它的链接。

<a id="prompts"></a>

## 提示词

设置 › Git 中有告诉智能体如何撰写提交信息和拉取请求的提示词：`commit-message-prompt` 和 `pr-message-prompt`。在你修改之前，它们显示 Kero 自己的提示词，**恢复默认** 可以恢复。那里的审查提示词 `pr-review-prompt` 是交给审查智能体的指示，`pr-guide-prompt` 则是交给导览智能体的指示。在审查标签页的 **仓库设置…** 中，可以为单个仓库替换前三个提示词；未改动的提示词沿用设置中的。

## 在命令行中

```sh
kero pr list -p api --json          # 仓库中打开的拉取请求
kero pr review 123 -p api           # 智能体在工作树中审查，与审查标签页的启动方式相同
kero pr review 123 -p api --guide   # 智能体编写它的审查导览
kero pr checkout 123 --worktree -- claude
kero pr state 123                   # 是否打开、是否草稿、能否合并、可用哪些方式
kero pr merge 123 --squash --delete-branch
```

`kero pr review` 需要应用已打开，且除非由 [Ama](./ama.md) 运行，还需要远程控制。智能体用来撰写草稿审查和导览、以及操作拉取请求的命令，见[命令行](./cli.md#draft-reviews)。
