# ワークツリー

1 つのチェックアウトで並んで作業するエージェントは、互いの変更につまずきます。専用の git ワークツリーで動くセッションは、自分のブランチで、自分のフォルダで作業するので、エージェントはあなたのチェックアウトに触れずに編集、ビルド、コミットができます。

## ワークツリーでセッションを始める

**セッション › ワークツリーで新規セッション…**（<kbd>⌘</kbd> <kbd>⌥</kbd> <kbd>T</kbd>）は**ワークツリーで**を有効にした[新規セッションのダイアログ](./sessions.md#new-session-dialog)を開き、ワークツリーでセッションを開始します: 選んだブランチ、または名前を付けてリポジトリのデフォルトブランチから作った新しいブランチをチェックアウトするワークツリーです。サイドバーのプロジェクトのメニューにもあり、そのプロジェクトのリポジトリのセッションを開始します。メニューバーのない Windows と Linux では、メニューバーのメニューは設定の隣にあるサイドバーの**メニュー**ボタン（⋯）にあります。

セッションはリポジトリのプロジェクトに入り、サイドバーにはそのブランチが表示されます。ほかの始め方:

- 履歴タブの[ワークツリーのセクション](#the-worktrees-section)の **+**、またはコミットの **ここからワークツリーで新規セッション…** と **… を新しいワークツリーで開く**。
- ブランチの切り替えでのブランチのメニュー。そのブランチを専用のワークツリーのセッションで開きます。
- プルリクエストの **レビュー** と **新しいワークツリーにチェックアウト**（[プルリクエスト](./pull-requests.md)）。
- エージェントが自分のセッションをワークツリーに移す（[下記](#moving-a-session-into-a-worktree)）。
- コマンドライン:

```sh
kero new --worktree fix-login -- claude   # 専用のワークツリーで、新しいブランチのセッション
kero new --worktree fix-login --base dev  # dev から分岐する
kero worktree create fix-login -p api -- claude "fix the login"   # プロジェクトのリポジトリの
```

<a id="where-worktrees-go-and-what-they-start-from"></a>

## ワークツリーの置き場所と起点

- ワークツリーはリポジトリ内の `.kero/worktrees/<branch>` に置かれます。Kero はそれを `.gitignore` ではなく `.git/info/exclude` で無視します。ほかの場所に置くには `worktree-dir` を設定します。
- ワークツリーを作る前に、Kero は元のブランチを取得してリモートのブランチから作るので、ローカルの `main` が古くても問題ありません。オフラインのときや、ローカルのブランチにリモートにないコミットがあるときは、ローカルのブランチから作ります。常にローカルのブランチから作るには `worktree-from-origin = false` を設定します。
- 新しいブランチをデフォルトブランチではなくプロジェクトのフォルダのブランチから作るには `worktree-base = current` を設定します。

これらは **設定 › Git** にあります。セッションで `kero worktree status` を実行すると、新しいワークツリーがどの設定に従うかを表示します。

Kero はワークツリーを作るとき、次の順に準備します:

1. 元のブランチを取得し、ワークツリーをチェックアウトします。
2. [`.worktreeinclude`](#copying-ignored-files) に並べた無視されたファイルをコピーします。
3. ワークツリーに git のサブモジュールがあれば、それをチェックアウトします。
4. リポジトリに[セットアップスクリプト](#setup-scripts)があれば、セッションのエージェントの横で、またはエージェントより先に実行します。

ウインドウの右下のカードが各ステップの進み具合を示し、そこの **キャンセル** で準備を止められます。

<a id="copying-ignored-files"></a>

## 無視されたファイルのコピー: `.worktreeinclude`

新しいワークツリーには git が追跡するファイルしかありません。`.env`、`.claude/settings.local.json`、`CLAUDE.local.md` のような無視されたファイルも持っていくには、Claude Code のワークツリーと同じく、リポジトリのメインのチェックアウトの最上位にある `.worktreeinclude` に `.gitignore` の書式で並べます:

```gitignore
.env
.env.local
.claude/settings.local.json
CLAUDE.local.md
config/secrets/
```

Kero は、コミットされているかどうかにかかわらずメインのチェックアウトの `.worktreeinclude` を読み、一致して git が無視するファイルをメインのチェックアウトからコピーします。追跡されているファイルは、すでにワークツリーにあります。ワークツリーにすでにあるファイルはそのままです。`node_modules` とほかのワークツリーは飛ばし、丸ごと無視されたフォルダには、`cache/keep.txt` のようにその中のパスを指すパターンがあるときだけ入ります。これらのコピーはメインのチェックアウトのものなので、[整理](#cleaning-up-worktrees)ではワークツリー独自のものとして数えません。

<a id="setup-scripts"></a>

## セットアップスクリプト: `kero.json`

新しいワークツリーでパッケージをインストールしたりビルドしたりといった準備をするには、リポジトリの最上位に `kero.json` を置き、ワークツリーの作成時に実行するスクリプトを書きます:

```json
{
  "scripts": [
    { "name": "Install", "command": "bun install", "runOnWorktreeCreate": true }
  ]
}
```

| キー | 意味 |
| --- | --- |
| `name` | セットアップのカードに表示するスクリプトの名前（デフォルト: ファイルの名前） |
| `command` | シェルで入力するのと同じコマンド: `npm ci && npm run build` |
| `runOnWorktreeCreate` | `true` で、ワークツリーの作成時に実行します。Kero はこれを持つ最初のスクリプトだけを実行します |
| `async` | `false` では、エージェントはスクリプトが終わるまで待ちます。省略するか `true` なら、エージェントはその横ですぐに始まります |

スクリプトはセッションのターミナルの下のターミナルで、ワークツリーのフォルダで、あなたのシェル（`shell` 設定）を通して、次の変数を設定して実行されます:

| 変数 | 値 |
| --- | --- |
| `KERO_WORKTREE_PATH` | 新しいワークツリーのフォルダ |
| `KERO_PROJECT_ROOT` | リポジトリのメインのチェックアウト。そこからファイルをコピーしたりリンクしたりできます |
| `KERO_WORKTREE_BRANCH` | ワークツリーのブランチ |

- **`"async": false` のとき**は、スクリプトのターミナルが先に始まり、スクリプトが終わるとその上でエージェントが始まります。失敗したときも始まるので、エージェントが対処できます。テストを実行するための依存関係のように、エージェントが準備の完了を必要とするときに使います。
- **それ以外のとき**は、エージェントがすぐに始まり、スクリプトはその横で実行されます。
- ターミナルは、スクリプトが成功するかキャンセルすると閉じ、失敗すると出力とともに残ります。
- シェルが `cmd` のときは、Kero はコマンドの終わりを判断できません: スクリプトは実行され続け、それを待つエージェントはすぐに始まります。

Kero はスクリプトを、まず新しいワークツリーで、次にメインのチェックアウトで探し、それぞれで `t3.json` より先に `kero.json` を探します: Kero は同じ形式の [t3code](https://github.com/pingdotgg/t3code) の `t3.json` も読み、t3code と同じくそのスクリプトに `T3CODE_PROJECT_ROOT` と `T3CODE_WORKTREE_PATH` を渡します。そのため、`kero.json` をコミットすれば全員で準備を共有でき、メインのチェックアウトだけに無視したまま置けば自分用にできます。有効な JSON でないファイルは準備を失敗させ、カードがその理由を示します。

Kero がセッションのために作るワークツリーはどれもこれを実行します: 新規セッションのダイアログ、`kero new --worktree`、`kero worktree create`、`kero worktree handoff`、そしてプルリクエストのレビューや新しいワークツリーへのチェックアウトです。自分で `git worktree add` で作ったワークツリーでは実行されません。

準備がどうなったかを見るには、セッションで `kero worktree status` を実行して準備のステップを表示するか、`kerod.log`（[トラブルシューティング](./troubleshooting.md#logs)）を読みます。ログには `setup script of <worktree> runs in pane <pane>: <command>` と、各準備がどう終わったかが記録されます。

## ワークツリーのセッションを閉じる

セッションを閉じると、ワークツリーも削除するか尋ねます:

- **未コミットの変更がない:** 既定は「ワークツリーを削除」です。ブランチはマージ済みなら一緒に削除され、そうでなければコミットとともに残ります。
- **未コミットの変更がある:** Kero は失われるファイルの数を示し、既定は「ワークツリーを残す」です。
- **ほかのセッションがそのワークツリーで作業している:** ワークツリーは残り、Kero は尋ねません。

```sh
kero close fix-login --remove-worktree           # 閉じて、ワークツリーを削除する
kero close fix-login --remove-worktree --force   # 未コミットの変更があっても
```

<a id="moving-a-session-into-a-worktree"></a>

## セッションをワークツリーに移す

チェックアウトですでに作業しているエージェントは、別のセッションを始める代わりに、自分のセッションを会話ごと専用のワークツリーに移せます。エージェントがペインで `kero worktree handoff <branch>` を実行すると、新規セッションのものと同じようにワークツリーが作られ（新しいブランチの起点はデフォルトブランチ、または `worktree-base` の設定どおり、または `--base`）、そのセッションのものになります。エージェントのターンが終わると、Kero はワークツリーの同じフォルダでエージェントを再び起動して会話を再開し、`--prompt` が渡されていればそれを入力します。ほかのペインと、コミットしていない変更はそのまま残ります。Kero のスキルがエージェントにこの使い方を教えます。すでに専用のワークツリーを持つセッションは、もう移せません。

```sh
kero worktree handoff fix-login                          # デフォルトブランチから
kero worktree handoff fix-login --base HEAD --prompt "go on with the fix"
```

<a id="the-worktrees-section"></a>

## ワークツリーのセクション

履歴タブのスタッシュの下の **ワークツリー** セクションは、リポジトリのワークツリーを、削除したときに失われるものとともに一覧します。変更したファイルやどのリモートにもないコミットはオレンジで、何も失われないときは緑で *マージ済み* か *プッシュ済み* と表示されます。**プッシュ** はワークツリーのブランチをプッシュし、**セッションで開く** はそこで作業しているセッションを表示するか、新しく始めます。**ワークツリーを削除** は先に確認します。変更のあるワークツリーは **それでも削除** を選んだときだけ削除され、未プッシュのコミットがあるものはブランチを残し、何も失われないものは **ブランチごと削除** できます。セッションのために作られたワークツリーは、そのセッションとともに閉じます。メニューではパスのコピーや、そのブランチを今のブランチへマージでき、**見つからないワークツリーを整理** はフォルダが削除されたものを忘れます。**+** で新しいワークツリーでセッションを始めます。

ブランチの切り替えにも **ワークツリー** の下にワークツリーが一覧されます: ダブルクリックするとそのセッションを開きます。

<a id="cleaning-up-worktrees"></a>

## ワークツリーの整理

ワークツリーは増えていきます。**設定 › Git › ワークツリーの整理**をオンにすると、Kero は自分で作ったワークツリーを、起動時と 1 時間ごと、そして**今すぐ削除**を押したときに削除します。既定ではオフです。選んだ条件のいずれかに当てはまるものが削除されます:

- **使われていない期間**: その日数、コミット、チェックアウト、セッションがない。
- **プルリクエストがマージ済み**: ブランチの GitHub のプルリクエストが、ワークツリーのコミットでマージされた。`gh` に問い合わせるので、`gh` にサインインしている必要があります。
- **独自のコミットがない**: ブランチにデフォルトブランチ以外のコミットがない。
- **最後のセッションを閉じた**: そこで作業するセッションがなくなった（ワークツリーを残してセッションを閉じたときなど）。

削除するのは Kero のフォルダ（`.kero/worktrees` または `worktree-dir`）にあるワークツリーだけです。セッションが作業中のもの、git がロックしているもの、作って 10 分以内のもの、独自のもの（コミットされていない変更、追跡されていないファイル、ビルドで作り直せない無視されたファイル）があるものは削除しません。`.worktreeinclude` で持ち込んだようにメインのチェックアウトと同じ内容の無視されたファイルや、`node_modules`、`dist`、`build`、`target`、`.venv` などのフォルダは数えません。ブランチは、デフォルトブランチにすべて含まれていればワークツリーと一緒に削除され、そうでなければコミットごと残ります。

**プロジェクト**で、このコンピュータのプロジェクトに独自の条件（**カスタム**）を付けるか、整理しない（**オフ**、ワークツリーを残す）ようにできます。オフのプロジェクトがあるリポジトリは、ほかのプロジェクトの設定にかかわらずワークツリーを残します。

## コマンドラインから

```sh
kero worktree list -p api        # ワークツリー: 各ワークツリーのセッション、Kero が作ったか、削除で失うもの、整理の判定
kero worktree status             # このセッションのワークツリー、その準備、プルリクエスト、handoff できるか
kero worktree create fix-login -p api -- claude "fix the login"
kero worktree remove fix-login -p api --branch   # 履歴タブと同じように、ブランチごと削除する
kero worktree cleanup --dry-run  # 自動の整理が今削除するもの
kero worktree cleanup
kero worktree prune -p api       # フォルダがなくなったワークツリーを忘れる
```

`-p <project>` の代わりに `-d <folder>` で、リポジトリをそのフォルダで指定します。どちらもなければ、今いるフォルダのリポジトリです。`kero worktree remove` は履歴タブと同じようにワークツリーを削除します: Kero がセッションのために作ったワークツリーはそのセッションを閉じ、ほかのセッションが作業しているワークツリーは残ります。`--json` で `list`、`status`、`cleanup` を JSON で出力します。
